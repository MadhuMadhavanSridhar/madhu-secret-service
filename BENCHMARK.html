Simple scoring (100 points)

Meeting the requirements is the entry bar, not the score. With AI-assisted coding most builds will meet them, so points come from three numbers that differ between builds, minus 5 for each requirement missed.

Requirement checks (pass or fail; each run 3 times on a fresh stack, 2 of 3 to pass):

  1. Basics. Create and read back exact content (Unicode, 64 KiB); bad input gets 400. With a passphrase: the right one returns the content, a missing one is refused without using a view, wrong ones get the unknown-id 404 and burn no views, matching is exact, and the passphrase is never echoed (tests/check_passphrase.py).
  2. TTL. ttl_seconds=2, read after 4 s, get 404.
  3. Views and revoke. max_views=3 gives 3 reads then 404; delete with token gives 204 then 404; a wrong token leaves the secret readable.
  4. Race. 50 simultaneous GETs on a max_views=1 secret return exactly one 200, in all 5 trials.
  5. Unguessable IDs. 200 ids and tokens: no duplicates, no sequence, at least 128 bits; token not derivable from id.
  6. No existence oracle. Wrong passphrase and unknown id give the same status and body, median timing gap under 2 ms over 400 requests.
  7. Rate limits. 200 creates and 500 reads in 10 s from one IP each get a 429 with Retry-After, the first 10 of each are not limited, and the limit holds when every request spoofs X-Forwarded-For or similar headers (tests/ratelimit.js).
  8. No plaintext at rest. Canary content and passphrase absent from DB dumps, container filesystems and volumes.
  9. Clean logs. No canary, passphrase (right or wrong), deletion token (right or wrong), full share URL, full id or URL fragment in any service log, in raw, URL-encoded, base64 or hex form, including on error paths. The id is a bearer capability, so only a short prefix or hash may be logged. Create, read and delete are recorded with time and IP (tests/check_logs.py).
  10. Headers. Cache-Control: no-store and Referrer-Policy: no-referrer on every secret response; CSP on any HTML.
  11. Design note. DESIGN.md of at most 1,000 words with sections on the threat model, where keys live and how deletion deletes, names client-side or server-side encryption with a reason, and was committed no later than the first code file. Checked by tests/check_design.py; the organizer confirms the reason holds up.
  12. Metrics. GET /metrics returns 200 and changes with traffic; it holds no content, passphrase, token, full id, share URL or fragment in any encoding, no client IPs as label values, and no per-secret series (25 creates must add fewer than 25 series). Checked by tests/check_metrics.py.

The error rule stops a global lock from passing the race check for free.

A break counts when the organizer runs the attacker's reproducer on a fresh stack and it succeeds. Typical breaks: secret read after consume, delete or expiry; plaintext in a dump; more views than allowed; passphrase or deletion-token bypass; ids or tokens leaked via logs, /metrics or errors; rate-limit bypass.

Why the PDF alone is not enough

Ten builds can be scored on one scale only if four things are fixed first: the wire contract, how the harness gets inside each stack, the machine, and the rate-limit rules for the harness. The PDF leaves all four open, so the same suite would fail sound builds for format reasons and reward fast laptops.

Gap in the PDFWhat goes wrong with 10 buildsFix in this standard

The principle: everything is public: the contract, the 12 checks and the scripts that run them. Everyone self-tests before freeze. Canary values, marker strings and trial order are random on every run, so nothing can be hard-coded to pass. This departs from the PDF's hidden suite on purpose: the requirements are the entry bar, and points come from speed and the attack phase.

Wire contract (frozen)

Every build must accept these requests and return these shapes exactly; extra fields are allowed, missing or renamed ones fail the conformance check. The stack starts with docker compose up -d --build, listens on port 8080, and answers GET /healthz with 200 within 120 s.

Rules the harness depends on:

  • Headers. Every response from /secrets and /s/*, including errors, carries Cache-Control: no-store and Referrer-Policy: no-referrer. Any text/html response also carries a Content-Security-Policy.
  • Minimum quota. Each client IP gets at least 20 creates and 60 reads per minute without a 429. The suite needs that much for correctness checks and the 50-way race.
  • Must limit. 200 creates in 10 s from one IP, or 500 reads in 10 s, must produce at least one 429.
  • Client IP. By default the TCP peer address is the client. X-Forwarded-For, X-Real-IP and Forwarded are ignored unless the peer is in TRUSTED_PROXY_CIDRS.
  • Generator exemption. Every build honors the environment variable RATE_LIMIT_EXEMPT_CIDRS (comma-separated CIDRs never limited). The harness sets it only for the load test, never for the security suite.
  • Crypto mode. Server-side builds receive plaintext content and must encrypt it. Client-side builds also ship a client image (see bench.yaml) so the harness can encrypt the canary the way a browser would; the URL fragment then carries the key and the server never sees plaintext.

Entrant manifest: bench.yaml

Each repo ships a bench.yaml at its root so one harness can reach inside any stack. The harness also dumps every container filesystem (docker export) and every volume on its own, so the manifest only covers what generic tooling cannot see, such as an in-memory store.

name: alice                 # entrant handle, used on the scoreboard
crypto: server              # server | client
app_service: app            # compose service that serves port 8080
client_image: null          # client mode only: image with `enc` and `dec` commands
                            #   enc: stdin plaintext -> stdout JSON {content, fragment_key}
                            #   dec: stdin JSON {content, fragment_key} -> stdout plaintext
db_dump:                    # commands whose stdout must contain every stored value
  - service: redis
    cmd: ["sh", "-c", "redis-cli --user dump --pass \"$DUMP_PASS\" --scan | xargs -r -n1 redis-cli --user dump --pass \"$DUMP_PASS\" DUMP"]
notes: "Redis is memory only; no volumes."

What the harness does with it:

  1. Runs every db_dump command after creating canary secrets, and greps stdout for the canary in raw, base64, hex and URL-encoded forms.
  2. Exports every container and tars every named volume and bind mount through a helper container, then greps those archives the same way.
  3. Reads docker compose logs for all services.

A db_dump that hides data (for example, dumping only metadata keys) is itself a confirmed break. Builds with no database still list how to reach whatever holds the secrets.

How speed is measured

All performance runs happen on one bench machine, one build at a time, so the speed bands compare designs, not laptops. Laptop results never count; they are for practice only.

Bench machine setup:

  • One Linux host or one Docker Desktop VM pinned to 4 CPUs and 8 GB, nothing else running. Docker Desktop on Windows adds a host-port proxy stall, so the generator always runs inside the compose network, never from the host.
  • The generator container is pinned to its own CPUs (--cpuset-cpus), so it does not steal from the build under test.
  • RATE_LIMIT_EXEMPT_CIDRS is set to the generator's subnet for this phase only.
  • A reference build (the organizer's) runs before and after each entrant. If its p99 drifts more than 10% between those runs, the entrant's run is repeated.

Workload, k6 constant-arrival-rate:

PhaseRateDurationRequest mix
Warm-up (not scored)200 rps15 sSame mix

A request is an error if it times out (2 s), returns 5xx, or returns anything other than 201 for a create, 200 for a fresh read, and 404 for an unknown id.

Fallback if no shared machine exists: each entrant runs the reference build and their own build back to back on their laptop with the same script, and scores use the ratio to their own reference run. That is noisier, so use it only for practice rounds.

Attack phase rules

Assignments and scope:

  • Each entrant attacks 2 assigned builds, drawn so nobody attacks someone who attacks them. With 10 people every build is attacked twice.
  • Attackers get the target's repo, DESIGN.md and bench.yaml, and their own running copy of the stack.
  • In scope: HTTP to port 8080, and read-only docker exec into the target's containers to model a stolen disk or DB backup. Out of scope: the host, the Docker daemon, other people's machines, denial of service.
  • Window: 90 minutes, findings timestamped when submitted.

Rules:

  • Reproducer required. One file, repro.sh or repro.py, takes BASE_URL (and the compose project name if it uses docker exec), runs against a fresh docker compose up in under 2 minutes, and exits 0 only when the break works.
  • Organizer confirms by running it twice on the bench machine. No exit 0, no points.
  • Dedup. One root cause on one target is one break; the earliest submission wins. The same bug on a different target counts again.
  • No double penalty. If a requirement check already failed for that bug, the attacker still gets 5 but the defender loses nothing more.

Run day and scorecard

A full round takes about 5 hours on the bench machine: about 15 minutes of suite and load runs per build, then the 90-minute attack window and confirmation.

  1. Before freeze. Organizer publishes this standard, all check scripts (tests/ratelimit.js, check_passphrase.py, check_logs.py, check_metrics.py, check_design.py and the rest of the suite) and the reference build. Everyone runs them against their own stack until all 12 requirements are green.
  2. Freeze. Each entrant pushes a git tag round1-final with docker-compose.yml, DESIGN.md and bench.yaml at the root. Commits after the tag are ignored.
  3. Suite. Organizer clones every tag to the bench machine and runs bench suite <repo> 3 times on fresh stacks, then docker compose down -v between runs.
  4. Load. bench perf <repo> 3 times, reference build before and after, machine otherwise idle.
  5. Publish suite and performance scores, so attackers can see where defenses are already weak.
  6. Attack window. 90 minutes. Findings go into a shared folder as findings/<attacker>__<target>__<n>/ with README.md and the reproducer.
  7. Confirm and publish the final scoreboard. Each defender gets their findings and reproducers.

Every run writes one JSON file per build, so scores can be rechecked and compared across rounds:

{
  "entrant": "alice",
  "tag": "round1-final",

For later rounds, keep the harness, the manifest, the bench machine and the peer rules; swap only the wire contract and the check table.
